### Bounded financial and recovery reasoning

Expected properties were grounded in project intent and financial identity/conservation, rather than treating existing test assertions as requirements. Public operations must preserve the selected owner, FA2, exact nat ID and quantity through the final request. A current generation is required after the last account await; an applied operation and refreshed holdings are distinct observations. A returned hash with unknown application cannot safely become permission to repeat the same economic action. The approved contract/token and escrow destination must agree with the trade, independently of presentation metadata. Invalid reward terms fail pair lookup; approval-read failure deliberately adds the same owner/token/escrow approval and does not itself establish transaction success.

For direct `initiate_trade`, each list element—not merely the first—is checked for existing pair, all six stored terms and `sp.sender == user_wallet`. Paused and empty batches fail before transfers. Burn and redeem batches derive from stored mapping; sender tokens go to stored sink, escrow tokens to that same validated caller. Repeated valid trades require aggregate external balances; mismatch or insufficient custody in any element must reject the atomic sequence under the protocol oracle. External FA2 rejection/operator/ledger behavior remains outside available source. Moving tokens to the sink does not prove destruction of FA2 supply. Arbitrary malicious FA2 implementations are not certified by a matching transfer interface or embedded MockFA2.

For privileged entries, stored admin authorizes pause, rescue, XTZ withdrawal, set, update and cleanup; UI gating is not assumed. Set rejects existing IDs, including a later duplicate in the same call, and requires positive amounts/distinct FA2 addresses. Update requires an existing ID and leaves cardinality unchanged. Cleanup deletes/decrements only present IDs; duplicate/missing IDs enter failed-deletion output without a second decrement. Empty admin lists have no mapping effect. Rescue uses exact supplied nat/recipient from escrow custody; withdrawal uses positive mutez, available balance and stored admin. Self/contract recipients may reject, retaining protocol failure atomicity. Positive default XTZ and attached tez on other entries are custody ingress, not automatic trade consideration; admin withdrawal remains the recovery path. These are decisive source traces and protocol reasoning, not executed SmartPy tests or assertions about the originated release.

For configuration, exact source versions and review intent must survive JS/JSON/Admin boundaries; interrupted writes need either exact recovery or a visible blocked state. Schema rejects unknown keys, duplicate collection/exclusion entries, malformed nat text, nonpositive/unsafe amounts and same-FA2 enabled trade terms. Lock claims serialize cooperating writers; transaction snapshots validate exact bytes and stage hashes, preserve operation identity, and archive before inactive replacement. Source, target, base, partial replacement, rollback failure and replay have distinct journal states. Automatic projection does not consult that recovery decision, producing AUD-002-004. No real operational journal/lock/archive was read for recovery, deleted or changed by this investigation.

Shared startup serves both clients; Exchange also implements its own same-shape single request for refresh.

**Violated property / expected:** an incomplete page cannot establish zero inventory, no owned token or completed post-burn balance reduction. Fetch the relevant scoped balance or establish completeness; otherwise retain unknown.

**Actual:** shared `fetchNFTs` returns the first page as a complete array. Drops `fetchRedeemSupply` maps an omitted funded redeem token to `0`; wallet renderers omit eligible holdings. ### AUD-002-002 — An unresolved submitted hash permits repeating the economic action

**Medium — unintended repeat burn/redeem and fees following retry; another wallet approval is still required.** Sources: `drops/js/events.js:991–1259`; `exchange/js/exchange.js:1152–1395`; retained-balance retry functions in both modules; `shared/public-trade-ops.js` `pollForConfirmation`.

**Reachable precondition:** Beacon returns an operation hash, but confirmation times out or the provider becomes unavailable before an applied result is observed. The user has enough remaining tokens for two trades, and the indexer still reports the starting holdings. The first operation may have applied or still apply; the application has not proved failure.

**Expected:** preserve the submitted receipt/uncertainty and reconcile it before another request can repeat that intent. A known pre-submit failure may permit retry; unknown application differs from rejection.

**Actual:** retained-trade maps are populated only after `await pollForConfirmation`. On an earlier confirmation error, `finally` releases the in-flight guard without retaining the hash. Drops leaves the original selection available and labels the outcome `ERROR`. Exchange clears quantities but offers `RETRY BALANCES`; that path can reauthorize stale starting holdings because no retained submitted trade exists. The same request can then be submitted again.

**Executed evidence:** the repro reuses checked-in inert fixture definitions executing the current handlers. Drops returns a hash, throws at confirmation, then accepts an identical second request without reselect/reconnect/refresh/resolution. Exchange returns a hash, fails confirmation, executes real Retry Balances against unchanged holdings, then accepts the same selected unit trade again. Both captured payloads are identical. Controls: a confirmed Drops trade with unresolved holdings blocks repeat, and a failure at the final pre-submit account read makes no request and safely permits a later send. The confirmation-error boundary models the real poller's timeout/outage throw; no live chain effect or double execution was observed. An existing test explicitly expecting confirmation-error retry release does not supply an independent correctness oracle.

### Continuation reasoning and release identity

Admin operation reasoning distinguishes known pre-submit rejection, returned hash with unknown application, proven failure and proven application. Direct contract authorization remains authoritative even when UI authority is stale. Pair set rejects occupied/duplicate IDs atomically within one call; sequential drop calls can partially complete across batches. A rejection/false/throw halts remaining batches, earlier receipts stay in in-memory history, and reset/provider/network replacement prevents obsolete later requests/publication. Reload loses that in-memory receipt history; a subsequent overlap/status scan and the contract's occupied-ID checks remain separate evidence, not proof that an uncertain prior batch failed. Edit/cleanup must retain exact stored identities independently of local options (AUD-002-006/011). Confirmation and refreshed storage were followed through every current legacy and counted-matcher caller.

For local authoring, the meaningful order classes are edit before/after preview, apply before/after token expiry/source replacement, second apply during an owned pending request, close/reopen during each await, writer unavailable/blocked/recovery, committed apply followed by failed or drifted read-back, and provider replacement before old preview/send publication. API token deletion precedes execution; the writer still controls the actual filesystem effect. Request retirement can suppress obsolete UI but cannot cancel an already committed write. HTTP origin/nonce protection is not an administrator privilege check on the loopback filesystem; the authorized local operator is the trust boundary. API/state reads outside the writer lock cannot guarantee an atomic operational snapshot, while apply's lock/version validation still guards mutation.
