### AUD-003-001 — Stale Public wallet helper can disconnect a newer account

**Medium; active shared helper, timing-dependent.** A wallet read begun under account A must lose authority after a newer account event publishes B. `shared/beacon-setup.js` guards the original boot path but `getVerifiedPublicActiveAccount` lacks the corresponding generation fence before wrong-network cleanup. If the old A read resolves after a valid B event, it clears/publishes disconnection over B; Home, Drops, Exchange and Utility consume the shared state. A current valid read and stale same-network read do not produce this effect. [Wallet reproduction](repro/AUD-003-wallet-repro.mjs): `node --experimental-vm-modules audits/repro/AUD-003-wallet-repro.mjs`. Beacon event timing and a real wallet disconnect were not observed. This is the **same behavioral invariant as CHR-20261029-001 on a remaining helper entrypoint**, not proof that its repaired boot path regressed.

### AUD-003-002 — Unsafe Drops starting balance can strand a submitted hash

**Medium; conditional on an accepted unsafe balance.** A submitted operation hash must be durable before a post-send validation failure can make recovery ambiguous. `drops/js/events.js` converts the starting FA2 balance to Number and `shared/public-trade-ops.js` reserves a receipt without validating that new row; after an inert wallet request returns a hash, `submitted` rereads and rejects the journal for unsafe balance, so the hash is not persisted and reload encounters the invalid journal across account scopes. A balance of 5 completes the control path. [Receipt reproduction](repro/AUD-003-receipt-repro.mjs): `node audits/repro/AUD-003-receipt-repro.mjs`. A real eligible balance above `Number.MAX_SAFE_INTEGER`, signing and chain application were not demonstrated. This is adjacent to the AUD-002-002 durable-submission repair, with a new receipt-validation root cause.
