# Data duplication and transcription map

## Authority model today

**CURRENT STATE.** There is no single authority for a token/work. Authority is split by consumer:

- chain/TzKT: whether a token exists, active balance, escrow pause, pair storage, operation status;
- `shared/chain-registry.js`: contracts, endpoints, network labels, explicit ID mirrors;
- `admin-ui/src/titles/*.json`: Admin-local title authority;
- numeric files under `admin-ui/src/thumbs/**`: local image/key authority;
- Webflow CMS: public presentation fields and CMS item identity;
- `shared/drop-params/drop-params.js`: current configured drop intent;
- GitHub raw branch copies: deployment/publication parity signal for drop params.

The future record should not replace registry or chain authority. It should own operator-authored work facts and captured integration identities, then derive consumer outputs.

## High-risk transcription seams

### 1. Post-mint identity to local key

**OBSERVED BEHAVIOR.** Thumbnail input chooses the next existing numeric key (`assets/thumbs/scripts/thumbs.mjs:143-167`), while no mint result feeds the tool. The operator must ensure that key equals the intended collection/token mapping.

**RECOMMENDATION.** New-item mode must require `{collectionKey, verifiedTokenId}` and refuse to proceed if the output path exists or if the local title, chain token, CMS token, and record identity disagree.

### 2. HEN mainnet versus active-network IDs

**OBSERVED BEHAVIOR.** HEN's 17 CMS/title keys are sparse mainnet IDs while Shadownet thumbnail keys are 0-16. Existing explicit mapping is deterministic (`shared/chain-registry.js:34-53`).

**RECOMMENDATION.** The canonical identity is the minted network/contract/token tuple. Any environment mirror is a derived, explicit mapping. Never infer HEN mapping from title order, file order, or ascending position.

### 3. Public CMS versus local Admin presentation

**OBSERVED BEHAVIOR.** Admin intentionally ignores remote titles/images for normal UI and resolves local manifests (`admin-ui/src/utils/nft.js:691-755`), while the public Webflow pages use CMS-rendered rows (`drops/js/events.js:477-509`, `exchange/js/exchange.js:788-837`).

**RECOMMENDATION.** A pipeline is complete only when both generated local outputs and staged/live CMS state are verified against the same canonical facts. “Local integrated” and “CMS integrated” remain separate gates.

### 4. Editions, supply, and sold-out semantics

**OBSERVED BEHAVIOR.** Planned `totalSupply`, curated CMS Editions, minted supply, and current escrow balance are not the same quantity. The current checklist compares escrow balance to the plan, while public sold-out uses the live escrow balance (`admin-ui/src/features/drops/drops.checklist.controller.js:532-643`; `drops/js/events.js:818-922`).

**RECOMMENDATION.** Use separate names: `editionCount`, `dropInitialSupply`, `dropRemainingSupply`, `redeemAmountPerTrade`, and any verified `mintedSupply`. Never overload `supply` in the canonical model.

## Facts that should remain external authorities

- Network endpoints, contracts, and ID mirrors remain in `shared/chain-registry.js`.
- Token existence, operation result, pause, pair storage, and current balances remain chain/TzKT facts.
- Active drop intent remains in `shared/drop-params/drop-params.js`.
- Webflow item/asset identifiers remain returned external integration identities.
- Secrets and signer material never become authoring facts.

## Facts that should become enter-once authoring inputs

- collection key;
- exact title;
- source artwork reference/hash;
- intended edition/mint quantity and explicitly named semantics;
- collection-specific metadata not deterministically derivable;
- CMS-only curated values such as an approved exact slug when needed;
- mint configuration that is safe to store (no keys/secrets);
- explicit drop intent, defaulting to `none` and available only for eligible CANAAN records.

Everything else should be derived, captured from an authoritative response, or verified against an external authority.
